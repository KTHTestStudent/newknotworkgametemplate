## Standing rules

These ten rules apply to every game made from this template. A project changes one only by recording the exception in section 10.

| # | Rule | Enforced in |
| --- | --- | --- |
| R1 | Story runs on Knotwork. AI creates stub knots only; the human writes all prose. | Section 4 |
| R2 | Phaser is used only when the engine test in section 6 says so; otherwise plain HTML, CSS and JS. | Section 6 |
| R3 | The game is fully playable in a web browser and ships to itch.io as a zip. | Sections 6, 9 |
| R4 | Every screen is fully playable by touch, by controller, and by keyboard and mouse. | Section 6 |
| R5 | VFX, SFX and tutorial hooks exist from the first playable phase, not a later polish pass. | Section 7 |
| R6 | No game value is hard-coded. Every number, name and string lives in a data definition. | Section 5 |
| R7 | Work goes to the local models first; a cloud model takes a task only for a logged reason. | Section 2 |
| R8 | The repo is GitHub-ready from the first commit: README, licence, branches, ignore file, disclosure. | Section 8 |
| R9 | Prose is the last content step, written after the design freeze. | Order of work |
| R10 | The Auto-Disclosure-Tool is set up in the first commit and its declarations are updated in every phase. | Section 2 |

## Order of work

Each step has a gate; nothing moves on until the gate passes.

1. **Repo.** Create the repo from the first-commit checklist in section 8, with this GDD and the disclosure tool in place. Gate: first commit pushed and the disclosure check passes.
2. **Concept.** Fill sections 1 to 3. Gate: the human approves the pillars, the core loop and the scope tiers.
3. **Story contract.** Fill the knot table in section 4 and create the stub knots. Gate: the story checker passes and every knot has exactly one outcome variable.
4. **Data.** Define the definition types and first-pass values in section 5. Gate: the validator passes.
5. **Input, feel and teaching plans.** Fill sections 6 and 7. Gate: every action has three bindings, every event has a VFX and SFX entry, and every mechanic has a tutorial step.
6. **Phased build.** Build one phase per fresh local session from the specs in section 8. Gate per phase: all checks pass.
7. **Balance and playtest.** Gate: the balance bar in section 3 is met and the human has played with each of the three input types.
8. **Design freeze.** Tag `design-freeze`. Rules, numbers and the story contract are fixed; presentation changes are still allowed.
9. **Prose.** The human writes every knot in Inky. Gate: the checker passes, every ending is reachable and no stub marker remains.
10. **Release.** Work through section 9 and tag the version.

## 4. Story contract (Knotwork)

The knot table is the whole interface between game and story: the game starts a knot, the knot returns one outcome.

### Rules

- One knot returns one outcome variable. A beat that needs two results becomes two knots.
- Tunnels stay inside ink and never talk to the game.
- Every ending choice keeps its line glued to the divert into `finish`, so the kit sends the outcome after the last line shows.
- AI creates stub knots only: the knot name, the outcome wiring and a visible `STUB` marker. AI writes no player-facing story sentence, not even as a placeholder.
- The beat note is a design comment for the writer and is never shown to the player.
- After the design freeze, `story.ink` is edited only by the human, in Inky.
- A release build fails its checks while any `STUB` marker remains.

| Knot | Beat note | Started by (game event) | Outcome variable | Values | Game effect per value | State |
| --- | --- | --- | --- | --- | --- | --- |
| \[knot\_name\] | \[what happens, in design terms\] | \[event\] | \[variable\] | \[a / b\] | \[a: effect; b: effect\] | \[Stub / Written\] |

### Stub knot shape

*Illustrative only: match it to the kit version in use, and treat the story checker as the authority.*

```ink
+ [STUB b]
    ~ outcome_var = "b"
    STUB b -> finish
```

## 5. Data definitions

Definitions are this template's version of Unity's ScriptableObjects: data assets kept in hand-editable files, loaded into a registry at boot and referenced by id. Code holds behaviour only.

### Rules

1. **Definition and instance are separate.** A definition is frozen after load. Runtime state lives in an instance that points to a definition id.
2. **One file per type** in `data/`, as JSON with comments or a plain text table a human can edit by hand.
3. **Reference by id.** Code and other definitions name a definition by its id string, never by position or by an imported constant.
4. **Every type has a schema.** The validator runs at boot in `#dev` and in the per-phase checks; it fails on unknown fields, missing references and out-of-range values.
5. **No literals in code.** Any number other than 0 and 1, and any player-facing string, comes from a definition. A lint check flags the rest.
6. **Strings are data.** Player-facing text lives in a strings table keyed by id, so the human can revise names and help text without touching code.
7. **Feel is data.** Timings, shake strength, volumes, dead zones and tutorial steps are definitions too.
8. **Data picks behaviour by key.** A definition names an effect such as `"effect": "burn"`; the code for it lives in a table in `src/`. Data never contains code.
9. **Live tuning.** `#dev` reloads definitions without a rebuild.
10. **Saves store ids.** A save holds instance state, definition ids and the data version, never copied values.

### Definition types

*The first seven rows exist in every game. Add the game's own types below them.*

| Type | File | Key fields | Referenced by | Tuned by |
| --- | --- | --- | --- | --- |
| GameConfig | `data/config.jsonc` | base resolution, save version, seed rules | boot | \[who\] |
| Difficulty | `data/difficulty.jsonc` | multipliers, bot skill | modes | \[who\] |
| InputMap | `data/input.jsonc` | action, bindings per device | input layer | \[who\] |
| FeelEvent | `data/feel.jsonc` | VFX id, SFX id, duration, shake | every system | \[who\] |
| Sfx | `data/sfx.jsonc` | waveform, envelope, pitch, volume | FeelEvent | \[who\] |
| TutorialStep | `data/tutorial.jsonc` | trigger, prompt string id, done condition | tutorial system | \[who\] |
| Strings | `data/strings.jsonc` | id, text | UI, tutorial | Human |
| \[Unit / Card / Enemy / Level\] | `data/[type].jsonc` | \[fields\] | \[systems\] | \[who\] |

### Example

```jsonc
// data/enemies.jsonc
{
  "id": "enemy.crow",
  "name": "str.enemy.crow.name",   // strings table id
  "hp": 6,
  "attack": 2,
  "onHit": "feel.hit.light",       // FeelEvent id
  "behaviour": "swoop"             // key into the code table
}
```

### Input rules

- Game code reads actions, never keys or buttons. Bindings live in `data/input.jsonc`.
- Every action is reachable by touch, by controller, and by keyboard and mouse. A feature that fails this on one device is not done.
- Nothing depends on hover. Anything a mouse shows on hover is also shown on tap or long-press and on controller focus.
- Nothing depends on drag alone. Each drag has a tap-then-tap or focus-then-confirm equivalent.
- Touch targets are at least \[48\] CSS px with space between them and clear of the screen's safe areas.
- Controller play never needs a pointer: every screen has focus navigation with a visible focus ring, on D-pad and stick.
- Prompts show the glyphs of the device used last.
- The game takes focus on the first click or tap, starts audio only after that gesture, and pauses when the tab is hidden or the controller disconnects.
